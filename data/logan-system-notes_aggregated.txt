#theloganproject
## SECURITY & OPERATIONAL RESILIENCE POLICY

### PURPOSE
To protect all digital and physical assets of The Logan Group and its divisions against theft, loss, corruption, and unauthorized access, while ensuring operational continuity.

### PRINCIPLES
1. **Defense in Depth:** Multiple layers of security.
2. **Least Privilege:** Access granted only as necessary.
3. **Verification Over Trust:** Assume breach; verify continuously.
4. **Resilience Over Perfection:** Systems must degrade gracefully and recover.
5. **Documentation & Auditing:** All security practices must be documented and auditable.

### ASSET CLASSIFICATION & PROTECTION

#### Class A: Foundational Assets (Highest Protection)
- Private cryptographic keys (hardware wallets, SSH keys, PGP)
- Legal documents, charters, identification
- Financial account credentials
- Unpublished original research and source code
- Backup seed phrases and recovery information

**Protection Rules:**
- Never stored in plaintext digitally.
- Encrypted, offline, and/or hardware-secured.
- Access requires multi-factor authentication (MFA) and documented reason.
- Regular integrity verification.

#### Class B: Operational Assets (High Protection)
- Project source code repositories
- System configuration files
- Internal documentation and wikis
- Build and deployment scripts
- Academic work in progress

**Protection Rules:**
- Version-controlled with signed commits.
- Access logs maintained.
- Encrypted at rest where feasible.
- Regular backups to separate, secure locations.

#### Class C: Public & Distribution Assets (Standard Protection)
- Published white papers
- Public website content
- Released software binaries
- Educational materials intended for free distribution

**Protection Rules:**
- Integrity checks (e.g., checksums, signatures) provided for downloads.
- Protected against defacement (read-only publishing pipelines).
- Mirrored for availability.

### ACCESS CONTROL POLICY
- **Personal Devices:** Full-disk encryption required. Automatic locking enabled.
- **Authentication:** Strong, unique passwords managed via a password manager. MFA required for all critical services (email, GitHub, cloud providers, financial).
- **Network:** Home network segmentation where possible. No sensitive operations on public Wi-Fi without a trusted VPN.
- **Servers & Infrastructure:** SSH key-based authentication only. Root login disabled. Firewalls configured to allow minimal necessary ports.

### BACKUP & RECOVERY POLICY
**3-2-1 Backup Rule:**
- **3** copies of important data.
- **2** different media types (e.g., SSD + cloud).
- **1** copy stored offsite (geographically separate).

**Backup Schedule:**
- **Class A Assets:** Encrypted, incremental, daily. Verified weekly.
- **Class B Assets:** Version-controlled (implicit backup). Full system snapshot monthly.
- **Class C Assets:** Archived upon major version release.

**Recovery Testing:** Annual restoration drill from backups to verify integrity and process.

### INCIDENT RESPONSE PLAN
1. **Identification:** Detect and confirm a security incident.
2. **Containment:** Isolate affected systems to prevent further damage.
3. **Eradication:** Remove the cause (malware, unauthorized access).
4. **Recovery:** Restore systems from clean backups.
5. **Lessons Learned:** Document the incident and improve defenses.

**Communication:** Guardian must be notified immediately for any incident involving financial loss, legal exposure, or data breach.

### CRYPTOGRAPHIC STANDARDS
- **Encryption at Rest:** AES-256-GCM or equivalent.
- **Encryption in Transit:** TLS 1.3 or equivalent.
- **Hashing:** SHA-256 or stronger for integrity.
- **Key Management:** Hardware security modules (HSM) or hardware wallets for cryptographic keys. No long-term keys stored on internet-connected machines.

### PHYSICAL SECURITY
- Hardware wallets and backup seeds stored in a fireproof, waterproof safe.
- Primary computing devices kept in a secure, private location when not in use.
- No sensitive information written down in unsecured notebooks.

### SOFTWARE DEVELOPMENT SECURITY
- Dependencies are regularly audited for known vulnerabilities.
- Code reviews (self-review or with guardian) before major commits.
- Secrets (API keys, passwords) never committed to version control.
- Use of static analysis tools where applicable.

### POLICY COMPLIANCE & REVIEW
- This policy is reviewed and updated quarterly.
- All system changes are evaluated for security impact.
- Breach of this policy may result in suspension of project work until remediation.

# 058 – Logan Writing: Rapid Story Publishing Plan

## 1. Purpose

**Logan Writing** is a streamlined system for turning story ideas into published works – fast.  
It prioritizes **completion over perfection**, **momentum over revision**, and **consistent output over sporadic brilliance**.

This plan is designed for writers who want to publish short stories, novellas, serial fiction, or even novels without getting stuck in endless editing or writer’s block.

## 2. Core Philosophy

| Principle               | Meaning                                                                 |
| ----------------------- | ----------------------------------------------------------------------- |
| **Done is better than perfect** | A published 70% draft is infinitely more valuable than an unpublished 100% draft. |
| **Speed creates clarity**      | Writing fast forces you to make decisions and find your authentic voice. |
| **No rewrites until it’s out**  | First publication is a “director’s cut” – you can revise later if needed. |
| **Quantity leads to quality**   | Volume builds skill faster than agonizing over one piece.               |

## 3. The Logan Writing Workflow (3 Phases)

### Phase 1: Pre‑write (30 min max)
- **Spark** – one sentence premise (who, what, why conflict).
- **Beat sheet** – 5–7 bullet points covering beginning, middle, end.
- **Character short** – name + one desire + one flaw (two sentences).
- **Stop** – do not outline further. The rest emerges while writing.

### Phase 2: Draft (1–3 hours, uninterrupted)
- **Timer method**: Write in 25‑minute sprints with 5‑minute breaks.
- **No editing** – typos, bad sentences, plot holes are allowed.
- **No re‑reading** previous paragraphs until the draft is finished.
- **Target lengths**:
  - Flash fiction (<1000 words) → 1 sprint
  - Short story (2000–5000 words) → 3–5 sprints
  - Novella (10k–20k words) → 2–3 days of sprints
- **If stuck** – type `[FIGHT SCENE HERE]` or `[RESOLVE LATER]` and keep moving.

### Phase 3: Polish & Publish (same day or next day, ≤1 hour)
- **One pass only**:
  - Fix obvious typos and grammar (spellcheck + read aloud once).
  - Ensure the first paragraph hooks.
  - Ensure the last paragraph lands.
- **No structural edits** – those are for “version 2.0” after publication.
- **Format** – use a simple template (see section 6).
- **Publish** – upload to your chosen platform (blog, Substack, Medium, Wattpad, Kindle, etc.).

## 4. Anti‑Burnout & Sustainability Rules

| Rule | Why |
|------|-----|
| **One story per week minimum** | Maintains rhythm without pressure. |
| **One day off per week from writing** | Prevents creative exhaustion. |
| **No more than 4 hours of writing in a single day** | Diminishing returns after that. |
| **Publish even if you hate it** | Hate is often just fear – push through. |
| **After 3 consecutive “bad” stories** → take a week off and read instead | Resets perspective. |

## 5. Serial Publishing (for ongoing readers)

If you’re publishing a serial (e.g., chapters every week):

- **Always keep 2 chapters ahead** of your publication schedule (similar to sermon buffer).
- **Each chapter must be a self‑contained scene** – ends with a minor hook or question.
- **Do not go back to revise earlier chapters** until the serial is complete.
- **At completion**, you may release a “collected edition” with revisions.

## 6. Templates for Speed

### Flash / Short Story Template (copy‑paste into your editor)

Indented code block (use 4 spaces or a tab):

    # [TITLE]

    **Logline**: [one sentence]

    **Characters**: [Name] – [desire] – [flaw]

    ---

    [First line – action or dialogue]

    [Continue writing – no breaks, no editing]

    ---

    **The End**

    *First draft completed on [date]*  
    *Published without revision (except typos)*

### Chapter Template (for serials)

    # [Book Title] – Chapter [X]

    **Previously**: [1 sentence recap]

    ---

    [Scene starts in media res]

    ---

    **Next chapter**: [1‑sentence tease]

## 7. Tools & Environment

|---------|-------------|

| Backup | Save to Obsidian folder `200-writing/raw-drafts/` |

| Voice dictation (optional) | Use for rough drafts when typing slows you down |

## 8. Measuring Progress

Track these weekly metrics (keep in Obsidian `210-writing-log.md`):

- **Stories published** this week / target (1)
- **Total words drafted** (aim for 3000–5000)
- **Hours spent writing** (aim for 5–8)
- **Number of times you edited before finishing draft** (target = 0)

If any week misses target, do **not** double next week. Simply reset.

## 9. Overcoming Common Blocks

| Problem | Logan Writing solution |
|---------|------------------------|
| “I don’t know how to start” | Write the last sentence first, then write toward it. |
| “My writing is terrible” | Yes, it is. Publish anyway. Terrible published > perfect invisible. |
| “I need more research” | No you don’t. Invent or bracket `[RESEARCH: X]` and move on. |
| “I’m afraid of bad reviews” | No one will read your first 10 stories. That’s freedom. |
| “I keep rewriting the first page” | Delete the first page after finishing. Start at page 2. |

## 10. The 30‑Day Launch Challenge

For absolute beginners: publish one story every day for 30 days.

- Each story: 300–1000 words.
- Max 45 minutes per story.
- No exceptions.
- After 30 days, you will have:
  - Killed perfectionism
  - Found your natural voice
  - Built an audience (even a small one)
  - Enough material for a collection

Then switch to the weekly plan above.

#theloganproject
## MENTAL MODEL & DECISION FRAMEWORKS

### 1. THE CORE LOOP: LEARN → BUILD → DOCUMENT → REFLECT
**Purpose:** A perpetual cycle that turns time into permanent, compounding intellectual capital.

**Steps:**
1.  **Learn:** Acquire knowledge through courses, reading, or research. Output: Notes.
2.  **Build:** Apply knowledge to create something tangible (code, essay, system). Output: Artifact.
3.  **Document:** Formally describe the artifact, its design, and its purpose. Output: White paper / README.
4.  **Reflect:** Analyze the process, outcomes, and lessons. Output: Journal entry & system adjustment.

**Rule:** A learning cycle is incomplete without at least one tangible output (Build, Document, or Reflect).

### 2. THE HIERARCHY OF WORK: URGENT vs. STRATEGIC
**Four Quadrants:**
- **Q1 (Urgent & Strategic):** Critical academic deadlines, security incidents, health issues. **Do immediately.**
- **Q2 (Not Urgent & Strategic):** Long-term project development, skill-building, research, exercise, planning. **Schedule and protect.**
- **Q3 (Urgent & Not Strategic):** Most emails, interruptions, minor bug fixes. **Delegate, minimize, or batch.**
- **Q4 (Not Urgent & Not Strategic):** Mindless browsing, entertainment, trivia. **Eliminate or strictly limit.**

**Rule:** Maximize time in Q2. It is the source of all long-term advantage.

### 3. THE ALLOCATION TRILEMMA (TIME, MONEY, ATTENTION)
**Principle:** You can optimize for two, but never all three simultaneously.
- **Project Mode (Time + Attention):** Spend time and deep focus to build with minimal money (e.g., coding, writing).
- **Leverage Mode (Money + Attention):** Spend money to save time, guided by attention (e.g., buying a tool, book, or course).
- **Automation Mode (Time + Money):** Spend time and money to build systems that preserve future attention (e.g., setting up automated investing, backup scripts).

**Rule:** Attention is the scarcest resource. Never spend it without a clear return in learning or asset creation.

### 4. THE PORTFOLIO LENS: DIVERSIFICATION OF INTELLECTUAL RISK
**Analogous to a financial portfolio, build an intellectual portfolio:**
- **Core Holdings (Index Funds):** Foundational skills (math, writing, programming fundamentals). Low "risk," high long-term return. Receive consistent, scheduled investment.
- **Growth Holdings (Stocks):** Specialized, deep projects (Build-Your-Own-Compiler, OS research). Higher "risk" (might not succeed), potential for outsized return (elite portfolio piece).
- **Alternative Assets (Crypto/Ventures):** Experimental, fringe, or interdisciplinary explorations (e.g., privacy tech, game design, philosophy). High "risk," potential for unique differentiation.

**Rule:** Rebalance periodically. Foundational skills (Core) must never fall below 50% of total time/energy allocation.

### 5. THE NARRATIVE PRINCIPLE: EVERYTHING IS A STORY
**Principle:** Isolated achievements are less valuable than a coherent narrative.
- For college admissions: The narrative is "independent scholar and systems builder."
- For future investors: The narrative is "founder of a sustainable knowledge institution."
- For oneself: The narrative is "lifelong learner building multi-generational impact."

**Rule:** All projects and learning should, directly or indirectly, support and strengthen the core narrative. Avoid random, unrelated efforts.

### 6. THE VALLEY OF DISAPPOINTMENT
**Concept:** After initial excitement, progress becomes invisible, difficult, and slow. Most give up here.
- **Application:** Expected in language learning, mastering a framework, writing a research paper, building a complex system.
- **Antidote:** Trust the system. Rely on process (daily time blocks, weekly reviews) over motivation. Document the struggle—it becomes part of the narrative.

### 7. THE 10-YEAR DECISION FRAMEWORK
**Question:** "Will this action/decision/habit matter in 10 years?"
- **Yes:** Prioritize highly. (E.g., building a research habit, investing, learning fundamentals, maintaining health.)
- **No:** Limit or eliminate. (E.g., arguing online, chasing short-term trends, most entertainment.)

**Rule:** Let the 10-year vision dictate weekly actions.

### 8. THE TWO MINDETS: STUDENT vs. ARCHITECT
- **Student Mindset:** Primary goal is to understand. Focus is on input (learning, consuming). Attitude is receptive.
- **Architect Mindset:** Primary goal is to create. Focus is on output (building, designing, synthesizing). Attitude is directive.

**Rule:** Schedule time for both, but always aim to transition Student learning into Architect output within one cycle.

- System call interface

**Out of Scope:**
- Production readiness

3. **Documentation as Proof** – All serious work must be documented clearly and truthfully.
4. **Long-Term Thinking** – Decisions are evaluated for multi-year or multi-decade impact.

## SECURITY & OPERATIONAL RESILIENCE POLICY

### PURPOSE
To protect all digital and physical assets of The Logan Group and its divisions against theft, loss, corruption, and unauthorized access, while ensuring operational continuity.

### PRINCIPLES
1. **Defense in Depth:** Multiple layers of security.
2. **Least Privilege:** Access granted only as necessary.
3. **Verification Over Trust:** Assume breach; verify continuously.
4. **Resilience Over Perfection:** Systems must degrade gracefully and recover.
5. **Documentation & Auditing:** All security practices must be documented and auditable.

### ASSET CLASSIFICATION & PROTECTION

#### Class A: Foundational Assets (Highest Protection)
- Private cryptographic keys (hardware wallets, SSH keys, PGP)
- Legal documents, charters, identification
- Financial account credentials
- Unpublished original research and source code
- Backup seed phrases and recovery information

**Protection Rules:**
- Never stored in plaintext digitally.
- Encrypted, offline, and/or hardware-secured.
- Access requires multi-factor authentication (MFA) and documented reason.
- Regular integrity verification.

#### Class B: Operational Assets (High Protection)
- Project source code repositories
- System configuration files
- Internal documentation and wikis
- Build and deployment scripts
- Academic work in progress

**Protection Rules:**
- Version-controlled with signed commits.
- Access logs maintained.
- Encrypted at rest where feasible.
- Regular backups to separate, secure locations.

#### Class C: Public & Distribution Assets (Standard Protection)
- Published white papers
- Public website content
- Released software binaries
- Educational materials intended for free distribution

**Protection Rules:**
- Integrity checks (e.g., checksums, signatures) provided for downloads.
- Protected against defacement (read-only publishing pipelines).
- Mirrored for availability.

### ACCESS CONTROL POLICY
- **Personal Devices:** Full-disk encryption required. Automatic locking enabled.
- **Authentication:** Strong, unique passwords managed via a password manager. MFA required for all critical services (email, GitHub, cloud providers, financial).
- **Network:** Home network segmentation where possible. No sensitive operations on public Wi-Fi without a trusted VPN.
- **Servers & Infrastructure:** SSH key-based authentication only. Root login disabled. Firewalls configured to allow minimal necessary ports.

### BACKUP & RECOVERY POLICY
**3-2-1 Backup Rule:**
- **3** copies of important data.
- **2** different media types (e.g., SSD + cloud).
- **1** copy stored offsite (geographically separate).

**Backup Schedule:**
- **Class A Assets:** Encrypted, incremental, daily. Verified weekly.
- **Class B Assets:** Version-controlled (implicit backup). Full system snapshot monthly.
- **Class C Assets:** Archived upon major version release.

**Recovery Testing:** Annual restoration drill from backups to verify integrity and process.

### INCIDENT RESPONSE PLAN
1. **Identification:** Detect and confirm a security incident.
2. **Containment:** Isolate affected systems to prevent further damage.
3. **Eradication:** Remove the cause (malware, unauthorized access).
4. **Recovery:** Restore systems from clean backups.
5. **Lessons Learned:** Document the incident and improve defenses.

**Communication:** Guardian must be notified immediately for any incident involving financial loss, legal exposure, or data breach.

### CRYPTOGRAPHIC STANDARDS
- **Encryption at Rest:** AES-256-GCM or equivalent.
- **Encryption in Transit:** TLS 1.3 or equivalent.
- **Hashing:** SHA-256 or stronger for integrity.
- **Key Management:** Hardware security modules (HSM) or hardware wallets for cryptographic keys. No long-term keys stored on internet-connected machines.

### PHYSICAL SECURITY
- Hardware wallets and backup seeds stored in a fireproof, waterproof safe.
- Primary computing devices kept in a secure, private location when not in use.
- No sensitive information written down in unsecured notebooks.

### SOFTWARE DEVELOPMENT SECURITY
- Dependencies are regularly audited for known vulnerabilities.
- Code reviews (self-review or with guardian) before major commits.
- Secrets (API keys, passwords) never committed to version control.
- Use of static analysis tools where applicable.

### POLICY COMPLIANCE & REVIEW
- This policy is reviewed and updated quarterly.
- All system changes are evaluated for security impact.
- Breach of this policy may result in suspension of project work until remediation.

## MENTAL MODEL & DECISION FRAMEWORKS

### 1. THE CORE LOOP: LEARN → BUILD → DOCUMENT → REFLECT
**Purpose:** A perpetual cycle that turns time into permanent, compounding intellectual capital.

**Steps:**
1.  **Learn:** Acquire knowledge through courses, reading, or research. Output: Notes.
2.  **Build:** Apply knowledge to create something tangible (code, essay, system). Output: Artifact.
3.  **Document:** Formally describe the artifact, its design, and its purpose. Output: White paper / README.
4.  **Reflect:** Analyze the process, outcomes, and lessons. Output: Journal entry & system adjustment.

**Rule:** A learning cycle is incomplete without at least one tangible output (Build, Document, or Reflect).

### 2. THE HIERARCHY OF WORK: URGENT vs. STRATEGIC
**Four Quadrants:**
- **Q1 (Urgent & Strategic):** Critical academic deadlines, security incidents, health issues. **Do immediately.**
- **Q2 (Not Urgent & Strategic):** Long-term project development, skill-building, research, exercise, planning. **Schedule and protect.**
- **Q3 (Urgent & Not Strategic):** Most emails, interruptions, minor bug fixes. **Delegate, minimize, or batch.**
- **Q4 (Not Urgent & Not Strategic):** Mindless browsing, entertainment, trivia. **Eliminate or strictly limit.**

**Rule:** Maximize time in Q2. It is the source of all long-term advantage.

### 3. THE ALLOCATION TRILEMMA (TIME, MONEY, ATTENTION)
**Principle:** You can optimize for two, but never all three simultaneously.
- **Project Mode (Time + Attention):** Spend time and deep focus to build with minimal money (e.g., coding, writing).
- **Leverage Mode (Money + Attention):** Spend money to save time, guided by attention (e.g., buying a tool, book, or course).
- **Automation Mode (Time + Money):** Spend time and money to build systems that preserve future attention (e.g., setting up automated investing, backup scripts).

**Rule:** Attention is the scarcest resource. Never spend it without a clear return in learning or asset creation.

### 4. THE PORTFOLIO LENS: DIVERSIFICATION OF INTELLECTUAL RISK
**Analogous to a financial portfolio, build an intellectual portfolio:**
- **Core Holdings (Index Funds):** Foundational skills (math, writing, programming fundamentals). Low "risk," high long-term return. Receive consistent, scheduled investment.
- **Growth Holdings (Stocks):** Specialized, deep projects (Build-Your-Own-Compiler, OS research). Higher "risk" (might not succeed), potential for outsized return (elite portfolio piece).
- **Alternative Assets (Crypto/Ventures):** Experimental, fringe, or interdisciplinary explorations (e.g., privacy tech, game design, philosophy). High "risk," potential for unique differentiation.

**Rule:** Rebalance periodically. Foundational skills (Core) must never fall below 50% of total time/energy allocation.

### 5. THE NARRATIVE PRINCIPLE: EVERYTHING IS A STORY
**Principle:** Isolated achievements are less valuable than a coherent narrative.
- For college admissions: The narrative is "independent scholar and systems builder."
- For future investors: The narrative is "founder of a sustainable knowledge institution."
- For oneself: The narrative is "lifelong learner building multi-generational impact."

**Rule:** All projects and learning should, directly or indirectly, support and strengthen the core narrative. Avoid random, unrelated efforts.

### 6. THE VALLEY OF DISAPPOINTMENT
**Concept:** After initial excitement, progress becomes invisible, difficult, and slow. Most give up here.
- **Application:** Expected in language learning, mastering a framework, writing a research paper, building a complex system.
- **Antidote:** Trust the system. Rely on process (daily time blocks, weekly reviews) over motivation. Document the struggle—it becomes part of the narrative.

### 7. THE 10-YEAR DECISION FRAMEWORK
**Question:** "Will this action/decision/habit matter in 10 years?"
- **Yes:** Prioritize highly. (E.g., building a research habit, investing, learning fundamentals, maintaining health.)
- **No:** Limit or eliminate. (E.g., arguing online, chasing short-term trends, most entertainment.)

**Rule:** Let the 10-year vision dictate weekly actions.

### 8. THE TWO MINDETS: STUDENT vs. ARCHITECT
- **Student Mindset:** Primary goal is to understand. Focus is on input (learning, consuming). Attitude is receptive.
- **Architect Mindset:** Primary goal is to create. Focus is on output (building, designing, synthesizing). Attitude is directive.

**Rule:** Schedule time for both, but always aim to transition Student learning into Architect output within one cycle.

**Mission Statement:**  
The Logan Group exists to unify education, research, and engineering into a single, disciplined system that prioritizes learning, depth, and long-term impact over short-term profit.

- To design and operate independent educational platforms
- To conduct technical and interdisciplinary research
- To build high-quality software and systems

The Organization operates under the following principles:

1. **Learning First** – Knowledge and understanding take priority over monetization.
2. **Depth Over Breadth** – Fewer projects done deeply are superior to many shallow efforts.
3. **Documentation as Proof** – All serious work must be documented clearly and truthfully.
4. **Long-Term Thinking** – Decisions are evaluated for multi-year or multi-decade impact.
5. **Integrity** – No misrepresentation of work, credentials, or outcomes.
6. **Sustainability** – No burnout, no reckless expansion, no unsound financial behavior.

The Organization functions as an umbrella structure consisting of multiple divisions, each with a defined role.

**Parent Organization:**

   - Cross-disciplinary research
   - Writing, reflection, and synthesis

4. **Infrastructure & Operations**
   - Documentation

**Decision Authority:**

**Transparency:**
- No hidden financial activity

- Monetization is optional, not mandatory

## PHYSICAL FITNESS & HEALTH READINESS (COLLEGE + LIFE)

**Purpose:**
- Meet or exceed all college fitness requirements
- Prepare for multiple physical assessments (not just PACER)
- Build lifelong health, discipline, and resilience
- Support cognitive performance and stress management

**Fitness Domains Colleges Commonly Assess:**
- Cardiovascular endurance
- Muscular strength and endurance
- Speed and agility
- Flexibility and mobility
- Body composition and general health

### CARDIOVASCULAR ENDURANCE
Examples of assessments:
- PACER test
- Timed mile or 1.5-mile run
- Shuttle runs
- VO₂ max–style endurance tests

**Training:**
- 2–3 sessions per week
- Mix of:
  - Steady-state cardio (jogging, cycling, swimming)
  - Interval training (short sprints + recovery)

**Goal:** Sustain effort over time without exhaustion

### STRENGTH & MUSCULAR ENDURANCE
Examples of assessments:
- Push-ups
- Sit-ups / curl-ups
- Planks
- Pull-ups

**Training:**
- 2–3 sessions per week
- Bodyweight focus (safe, equipment-free)

**Core exercises:**
- Push-ups
- Squats
- Lunges
- Planks
- Pull-ups or assisted pull-ups

**Goal:** Control your own body weight with good form

### SPEED, AGILITY & COORDINATION
Examples of assessments:
- Shuttle runs
- Agility drills
- Sports tryouts
- General movement evaluation

**Training:**
- Short sprint intervals
- Ladder drills
- Direction-change drills

**Goal:** Move efficiently and safely, not recklessly

### FLEXIBILITY & MOBILITY
Examples of assessments:
- Sit-and-reach test
- Mobility screens
- Injury-risk evaluations

**Training:**
- 10–15 minutes daily or every other day
- Stretching hips, hamstrings, calves, shoulders, back

**Goal:** Prevent injury and maintain long-term mobility

### GENERAL HEALTH & RECOVERY
Often overlooked but critical:
- Sleep quality
- Nutrition
- Hydration
- Stress management

**Rules:**
- 8–9 hours of sleep (non-negotiable)
- Balanced nutrition (protein, carbs, healthy fats)
- Hydration daily
- Rest days are part of training

### WEEKLY FITNESS STRUCTURE (BALANCED)
Example:
- 2x cardio
- 2x strength
- 1x speed/agility
- 1x mobility/recovery

**Rule:** Consistency > intensity, No burnout, Fitness supports academics, not competes with it

### MENTAL DISCIPLINE & PERFORMANCE
Fitness is also mental training:
- Builds focus
- Improves stress tolerance
- Enhances learning and memory

**Rule:** Physical discipline reinforces academic discipline

### LONG-TERM OUTCOME
This system ensures readiness for:
- PACER tests
- Timed runs
- Strength evaluations
- Sports tryouts
- General college health requirements
- Lifelong physical resilience

# 057 – Daily Sermons & Devotionals Self-Policy

## 1. Purpose

This policy defines a sustainable, anti‑burnout workflow for producing daily sermons and daily devotionals within **The Logan Project**.  
It ensures consistent output without compromising mental, spiritual, or physical health.

## 2. Core Requirements

| Requirement                | Description                                                                 |
| -------------------------- | --------------------------------------------------------------------------- |
| **Always stay 3 days ahead** | A minimum of three completed, ready‑to‑publish sermons/devotionals are always in the backlog. |
| **Increase buffer over time** | The backlog will be gradually expanded to create space for planned breaks, illness, or low‑energy periods. |
| **No burnout**             | Every rule, limit, and review process exists to protect long‑term capacity. |

## 3. Buffer Zone Definition

- **Minimum buffer** = 3 days of content (e.g., today is April 6 → ready content for April 7, 8, 9).
- **Target buffer** after 3 months = 5 days.
- **Target buffer** after 6 months = 7 days.
- **Maximum comfortable buffer** = 10 days (beyond this, diminishing returns – focus on rest instead).

> *Buffer days are measured in **ready‑to‑publish units** (editing done, metadata attached, scheduled if possible).*

## 4. Gradual Buffer Expansion Schedule

| Time from start | Minimum backlog | Comfortable backlog | Action                                       |
| --------------- | --------------- | ------------------- | -------------------------------------------- |
| Month 1         | 3 days          | 4 days              | Establish rhythm; no forced expansion        |
| Month 2–3       | 4 days          | 5 days              | Add 1 extra day when energy is naturally high |
| Month 4–6       | 5 days          | 7 days              | Consolidate; use light weeks to build ahead   |
| Month 7+        | 7 days          | 10 days             | Maintain; never exceed 10 unless for sabbatical |

> **Never expand the buffer by working overtime.** Expansion happens by **reducing other low‑priority tasks** or using naturally high‑energy windows.

## 5. Burnout Prevention Rules (Non‑negotiable)

1. **Daily cap**  
   - Maximum 2 hours total for *writing + editing* sermons/devotionals combined.  
   - If unfinished after 2 hours → stop. Tomorrow is another day.

2. **Weekly rest**  
   - One full day per week with **zero** work on sermons/devotionals.  
   - No backlog building, no editing, no topic brainstorming.

3. **Sabbath / ministry‑free weeks**  
   - Every 8 weeks → take 3 consecutive days off from content creation.  
   - Every 6 months → take one full week off (use built‑up backlog).

4. **Early warning system**  
   - If you feel *resistance*, *fatigue*, or *dread* before writing → skip that day and rely on backlog.  
   - Track mood after each session (1‑5 scale). Three days of ≤2 → force a 2‑day break.

5. **No “catch‑up” punishment**  
   - Falling behind never justifies overtime. Instead:  
     - Reduce length or depth of next 2‑3 pieces.  
     - Use a “low‑effort template” (scripture + 3 bullet reflection + prayer).  
     - Announce a short pause to your audience (they will understand).

## 6. Weekly Operating Routine

| Day       | Action                                                                 |
| --------- | ---------------------------------------------------------------------- |
| Monday    | Review backlog count. If <4 days, plan extra session for Tuesday.      |
| Tuesday   | Write 2 days of content.                                               |
| Wednesday | Write 1 day, edit yesterday’s 2 days.                                  |
| Thursday  | Edit, polish, schedule. Aim to reach 5‑day backlog.                    |
| Friday    | **No sermon/devotional work** (rest).                                  |
| Saturday  | Light review only – 30 min max (themes for next week, no writing).     |
| Sunday    | Write 1‑2 days if energy is high, otherwise rest.                      |

> Adjust days to fit your actual calendar. The key is **one full rest day** and **capped daily hours**.

## 7. Break & Emergency Protocol

### Planned breaks (vacation, retreat, illness)
- **Minimum 3 weeks’ notice** → build extra buffer (aim for 7–10 days).
- Upon return: take 2 days to **only restore buffer**, no new publication until backlog ≥4.

### Unplanned emergency
- Publish from backlog until it drops to **1 day left**.
- Then issue a short “pause” notification (template available in `018-risk-management-sustainability-policy.md`).
- No guilt, no apology tour – rest is a strategic asset.

## 8. Measuring & Review

Every **month** (last Friday) review these metrics:

- Average backlog size over the month  
- Number of days where daily cap was exceeded (target = 0)  
- Self‑reported energy before/after writing (1–5 scale)  
- Any skipped days because of dread/fatigue

If any red flag appears → reduce output by 20% for two weeks and re‑evaluate.

## 9. Integration with Obsidian & “The Logan Project”

- Store all unpublished sermons/devotionals in a dedicated folder:  
  `100-daily-content/queue/`  
- Use a simple status tag: `#backlog/day0` (today), `#backlog/day1` (tomorrow), etc.  
- Automate the count via a Dataview query (see example below).  

- Each piece must include a “published date” field in frontmatter.
    
- Weekly review note: `110-reviews/buffer-review-YYYY-WW.md`
    

## 10. Failure‑mode Handling

If you ever wake up and realise the backlog is **0**:

1. **Do not panic.**
    
2. Publish a short “Scripture & silence” reflection (5 min to write).
    
3. Take the day off anyway – one missed day is harmless.
    
4. Next day: rebuild to 3 days ahead using the **weekly routine**, not overtime.
    

This policy is **living**. Adjust numbers after 90 days based on real experience.
